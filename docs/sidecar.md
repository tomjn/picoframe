# Sidecars: long-lived local servers

Some plugins have substantial non-Rust business logic (parsing, ML, a large TS/Bun codebase) that is awkward to port to Rust and too slow to spawn per call. picoframe's **sidecar** pattern runs that logic as a **persistent localhost HTTP server** spawned once at app startup: no per-call cold start, and long operations can stream progress to the UI.

The reference implementation is the `worker` plugin (`plugins/worker` + `crates/tauri-plugin-picoframe-worker`); the reusable lifecycle lives in `picoframe_core::sidecar`.

## Architecture

```
+------------------+        spawn (externalBin / bun run)      +--------------------------+
|  Tauri (Rust)    |  ---------------------------------------> |  sidecar server (Bun)    |
|                  |                                           |  127.0.0.1:<ephemeral>   |
|  picoframe_core  |  <---- handshake file {port,token,pid} -- |                          |
|  ::sidecar       |                                           |  GET  /health            |
|                  |  ---- GET /health (bearer) -------------> |  POST /command -> CliResult
|                  |  ---- POST /command (bearer) -----------> |  GET  /events (SSE)      |
|                  |  <=== GET /events SSE (progress) ======== |                          |
|   app.emit(      |                                           +--------------------------+
|   "<prefix>/progress")  -> Tauri event -> React useSidecarProgress -> toast
+------------------+
```

## Transport: loopback TCP + bearer token

The transport is **127.0.0.1 TCP with a per-spawn shared-secret bearer token**, not a Unix domain socket. Windows AF_UNIX support is too inconsistent for a long-lived-server handshake, and picoframe targets Windows/macOS/Linux equally, so a single loopback-TCP path keeps the code uniform. The token (256 bits, generated by the Rust parent) gates every request; loopback keeps traffic off the network.

## Wire contract

The Rust parent passes these to the child via env:

| Env | Meaning |
| --- | --- |
| `PICOFRAME_SIDECAR_TOKEN` | shared secret every request must present as `Authorization: Bearer <token>` |
| `PICOFRAME_SIDECAR_HANDSHAKE` | path to write the `{port,token,pid}` handshake file (mode `0600`, atomic) once bound |
| `PICOFRAME_SIDECAR_PARENT_PID` | parent pid; the child self-exits if the parent disappears |
| `PICOFRAME_SIDECAR_HOST` | bind host (always `127.0.0.1`) |

Endpoints (all require the bearer token):

- `GET /health` -> `{ "ok": true }`
- `POST /command` with `{ "command": string, "args": object }` -> a `CliResult` (`{ success, data?, error? }`)
- `GET /events` -> `text/event-stream`; each `data:` line is a `ProgressEvent`

`ProgressEvent`: `{ type: "progress", op, status: "running"|"complete"|"failed", current?, total?, detail? }`.

## Lifecycle and orphan-proofing

`picoframe_core::sidecar` handles spawn -> handshake -> health poll -> SSE bridge -> crash restart -> kill-on-exit. Orphan-proofing is **bidirectional**, because tokio's `kill_on_drop` (and any parent-side kill) never runs if the parent is `SIGKILL`ed:

1. The Rust side kills the child on `RunEvent::Exit` and on drop.
2. The Bun child watches `PICOFRAME_SIDECAR_PARENT_PID` (`process.kill(ppid, 0)`) and self-exits — removing its handshake file — the moment the parent is gone.

Together these guarantee no server survives the app, even on a hard kill.

## Building a sidecar plugin

Mirror the `worker` plugin:

1. **Server** — `plugins/<x>/sidecar/server.ts`: a `Bun.serve` binding `127.0.0.1:0`, writing the handshake, checking the bearer token, and exposing `/health`, `POST /command`, and `GET /events`. Copy `plugins/worker/sidecar/server.ts`.
2. **Compile** — `plugins/<x>/scripts/build-sidecar.ts` runs `bun build --compile` to `binaries/<name>-<triple>` for Tauri's `externalBin`. Wire it into the app's `predev`/`prebuild` so it exists before the Rust build.
3. **Rust plugin** — `crates/tauri-plugin-picoframe-<x>`: call `Sidecar::spawn(app, SidecarOptions { bin, dev_command, event_prefix, .. })` in `setup`, `app.manage` the handle, and `sidecar.shutdown()` on `RunEvent::Exit`. Commands proxy to `sidecar.request(command, args)` (run under `spawn_blocking`).
4. **Frontend** — `plugins/<x>`: `defineCommand` bindings + a page that calls `useSidecarProgress("<event_prefix>")` for a live progress toast.
5. **Wire it** — register the plugin in `SIDECARS` (`packages/cli/src/wiring/sidecar.ts`) so `picoframe add <x>` declares the `externalBin`, and `picoframe doctor` validates it.

Under `tauri dev`, if the compiled binary is absent the Rust side falls back to the plugin's `dev_command` (`bun run server.ts`), so no compile step is strictly required for local dev.

## Progress UI

The frame owns the toast surface (`Toaster`, mounted by the layout) and exposes `useSidecarProgress(eventPrefix)`, which drives one self-updating [sonner](https://sonner.emilkowal.ski/) toast from the progress stream. Because npm-published plugins can only import from `@picoframe/frame` (not a consumer app's copied-in registry), this progress primitive is a frame export rather than a registry component.
